## Snapshot of the current configuration

- **Packaging + layout.** Hatchling builds `ml-playground` from `src/ml_playground` and force-includes `tools/`, which means the published wheel ships CLI and helper scripts that primarily serve contributor workflows.【F:pyproject.toml†L1-L95】
- **Runtime entry points.** `project.scripts` exposes Typer-based automation (`ml_playground.cli`) and task runners under `tools/`, so anything that trims dependencies must respect these command surfaces.【F:pyproject.toml†L41-L47】【F:src/ml_playground/cli.py†L1-L120】【F:tools/ci_tasks.py†L1-L120】
- **Dependency surface.** Core training paths rely on `torch`, `transformers`, `peft`, and TensorBoard integrations, which explains the tight pins in the manifest; meanwhile data preparation utilities emphasize pure-Python flows and memory-mapped artifacts.【F:pyproject.toml†L14-L39】【F:src/ml_playground/training/loop/runner.py†L1-L200】【F:src/ml_playground/data_pipeline/preparer.py†L1-L120】
- **Experimental extras.** LIT analysis code and experiment registries live under `src/ml_playground/analysis` and `experiments/`, but the `lit` extra is currently disabled for Python 3.13, signalling intent to gate non-core visualization tooling.【F:pyproject.toml†L49-L57】【F:src/ml_playground/analysis/lit/integration.py†L1-L170】
- **Tooling hub.** `pyproject.toml` centralises formatter, lint, type-checker, pytest, and cache conventions, reinforcing the repo policy that TOML is the single config source for developer automation.【F:pyproject.toml†L60-L220】

## Recommended practices and trade-offs

### 1. Enrich and future-proof packaging metadata

| ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Add `readme = { file = "README.md", content-type = "text/markdown" }`, SPDX license classifiers, project URLs, and keywords. | Improves discoverability if the CLI is distributed on PyPI and aligns with Hatch expectations for metadata completeness.【F:pyproject.toml†L7-L20】                                                                            | Friendly to downstream automation (pip metadata checks, docs generators). | Requires documentation owners to keep URLs/descriptions aligned with the living guideline set.【F:.dev-guidelines/DOCUMENTATION.md†L90-L150】                    |
| Distinguish `authors` from `maintainers`.                                                                                    | The repo is community maintained; clarifying maintainers mirrors the collaborative ownership seen in configuration modules and tests.【F:pyproject.toml†L9-L20】【F:tests/unit/training/loop/test_training_runner.py†L1-L200】 | Signals accountability, simplifies security contact.                      | Needs a process so maintainers are updated when teams change.                                                                                                    |

### 4. Align experiments and extras

- **Document experiment-specific dependencies.** Analysis modules call into LIT servers and TensorFlow datasets; listing these under named extras (`lit`, `analysis`) keeps optional flows explicit.【F:src/ml_playground/analysis/lit/integration.py†L1-L170】【F:src/ml_playground/analysis/lit/requirements.txt†L1-L40】 The trade-off is that experiment READMEs must mention which extras to install.【F:src/ml_playground/experiments/bundestag_char/Readme.md†L1-L120】
- **Audit dataset loaders before slimming dependencies.** Preparers default to local text files; only a subset of experiments imports HuggingFace datasets. Confirm actual runtime needs before removing `datasets` from the base install to avoid breaking CLI defaults.【F:src/ml_playground/experiments/bundestag_tiktoken/preparer.py†L1-L80】

## Differing viewpoints to weigh

1. **Strict vs. loose pinning.** Teams focused on determinism (e.g., mutation testing) prefer pins checked into `pyproject.toml`, while platform integrators favour ranges backed by `uv.lock`. Decide based on whether downstream consumers install from source or from lockfile snapshots.【F:pyproject.toml†L15-L39】【F:.github/workflows/mutation-suite.yml†L1-L120】
1. **Monolithic vs. split configuration.** Centralisation eases discovery but creates noisy diffs when multiple contributors edit tooling at once. Splitting config files trades the single-source ideal for targeted ownership (lint team vs. test team).【F:pyproject.toml†L125-L220】
1. **Dynamic versioning adoption.** Hatch SCM plugins minimise manual version bumps but complicate reproducible vendoring; static versions stay simple until automated releases are in place.【F:pyproject.toml†L7-L13】【F:.ldres/tv-tasks.md†L69-L110】

## Suggested decision workflow

1. **Stabilise metadata.** Draft the richer `[project]` metadata (maintainers, URLs, readme type) and review with documentation owners to ensure alignment with published guides.【F:pyproject.toml†L7-L20】【F:.dev-guidelines/DOCUMENTATION.md†L90-L150】
1. **Define dependency tiers.** Inventory actual imports across `src/ml_playground` to categorise which packages are core vs. optional, then adjust `dependency-groups` or extras accordingly.【F:src/ml_playground/cli.py†L1-L120】【F:src/ml_playground/analysis/lit/integration.py†L80-L170】
1. **Pilot build/runtime separation.** Remove build-only deps in a feature branch and validate onboarding via `uv run env-tasks setup` plus the CI quality gate to ensure no contributor impact.【F:tools/env_tasks.py†L1-L160】【F:tools/ci_tasks.py†L1-L200】
1. **Revisit version management.** Once release automation (tags, changelog) is scripted, evaluate switching to dynamic versions or adopt a documented manual bump checklist in `GIT_VERSIONING.md`.【F:.dev-guidelines/GIT_VERSIONING.md†L1-L160】【F:pyproject.toml†L7-L13】
